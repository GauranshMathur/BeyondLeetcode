Method. Every file was fetched by the agent in this session with `curl` from `raw.githubusercontent.com/<org>/<repo>/<sha>/<path>` and line numbers were read off the fetched file with `grep -n` and `sed -n`, never from memory. Every quoted string in the Chapters was then checked by a script against the lines its link cites (whitespace normalised, comment markers dropped; the quote's words appear in that order inside the cited range, and each link was narrowed to the quoted words). Where a quote renders markup, the table says so: the README of `antirez/rax` is Markdown, and the words quoted from it sit outside its code spans. The code blocks the Chapters show in full (`rax.h` lines 99 to 102, `mapping.go` lines 25 to 38, `cluster.c` lines 7685 to 7687 and 7710 to 7717) are copied line for line from the fetched file; the tables quote one line of each. Source types: 1 = source code, 2 = official documentation, 3 = standard, paper or the project's own README, 4 = a post by the system's own engineers.

## Observed, not cited

- **`rnodes`.** The rule in Problem 2 is written from `rax.h` lines 57 to 61 and 91 to 93, and `rax.c` lines 391 to 392 and 1095 to 1096. rax's own code was not compiled or run, so nothing here says Redis's node counter agrees with the rule after every sequence of inserts and deletes, and the Chapter and the statement say so. The rule gives 10 nodes for the first drawing of `rax.h`, 6 for the second, and 10 for the third (counted by hand from the drawings), and the Problem's Examples use those numbers.
- **The oracle.** The expected outputs of every Test come from a second implementation, a model that stores the keys in a dictionary and derives nodes, children and compression from the set of prefixes, with other techniques than the Reference Code (a sorted scan of a dictionary for `list` and `top`, a regular expression for `find`, every route length tried from 32 down for `match`, a minimum over specificity tuples for `serve`). It agreed with the Python Reference Code on 1,600 random scripts of 5 to 40 commands (four seeds of 400), and the Python, TypeScript (Node) and Go Reference Code agreed with it on 200 more.
- **Reference Code.** Python, TypeScript and Go were each run, locally, on every Test in each Problem's Submit scope (its own Tests and those of the Core Problems before it) before the content check: 600 runs, no difference.
- **Arithmetic the Chapters label as theirs.** 10, 6 and 10 nodes for the three drawings of `rax.h`; a child array of 2^k entries for a node that reads k bits, and at most 32 / k nodes on a 32-bit path; 26 slots of 8 bytes is 208 bytes; 16,384 slots fit two bytes; the worst case of a lookup in the Build's route table is 32 steps; the worst cases of the Build's `serve`, `find` and `list`. These are read off the loops, not claims about the systems.

## Leads that changed

- The issue's Chapter 1 ("The prefix tree and its node layout") is the Redis `rax` Chapter. Chapter 2 of the issue ("Compressed tries and radix trees in a real system", leads IP routing tables and an HTTP router) is split over three Chapters, because each part has its own system: the compression comments of `rax.h` are in Chapter 1, IP routing is Chapter 2 (Linux), and the HTTP router is Chapter 3 (Go).
- The issue's Chapter 3 ("Memory cost: array children versus map children") has no system of its own that states a memory cost. It is a section of Chapter 3: `mapping.go` for slice versus map, with the child array of the kernel's `tnode` (Chapter 2 below) and the packed node of `rax` as the two other layouts, and the 26-slot array as arithmetic. Nothing is claimed about how many bytes a Go map takes.
- The issue's Chapter 4 ("Prefix search and autocomplete") is the Redis Cluster slot index, which is a real prefix search. Autocomplete itself is only the Extra Problem `tries-top-k`; no Chapter sentence claims that any system does autocomplete this way.
- The XArray lead of `docs/research/candidates-hashing-heaps-trees.md` is not used. It needs a Chapter and a Core Problem of its own, and that note records that any statement about when or why the XArray replaced the radix tree has no source.

## Candidate Problems not in this Topic

- **Word Search II** is left out. It needs a two-dimensional board as input, and no Chapter's system has a board; it would not grow the same program. The other two candidates are in: Implement Trie is `tries-insert`, and Design Add and Search Words is the Extra `tries-wildcard-find` (framed by the ServeMux wildcard that matches one segment).

## Claims cut or rewritten for lack of a source

None ships as `[NEEDS SOURCE]`. While drafting, these were cut or rewritten until they had a source:

- "Go 1.22 is the first release with wildcard patterns": no source was fetched for it, so the sentence was cut.
- "Redis keeps several of its tables in a rax" and "its keys are also kept in order" (in the first draft): rewritten to the one line of `stream.h` that shows a stream's entries in a rax; the consumer-groups line and the claim about order were cut from that paragraph.
- "A rax key can hold any byte": rewritten to the `raxInsert` signature.
- "A Go map lookup is an expected O(1) operation": cut. `mapping.go` does not say how `map` is implemented; the Chapter says exactly that.
- Why the ServeMux authors chose 8, a decision tree, or why the kernel chose an LC-trie: not claimed. `mapping.go` says the limit "is a variable for benchmarking" and states a goal, and that is all the Chapters say. The design discussion of ServeMux was not fetched.
- "Level compression makes the tree shallower where routes are dense": rewritten to the arithmetic about 2^k entries.
