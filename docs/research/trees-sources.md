Method. Every file was fetched by the agent with `curl` from `raw.githubusercontent.com/<org>/<repo>/<sha>/<path>` on 2026-10-28 (the SQLite, Rust, Go and bfs files were first fetched at their tags, then again at the commit SHA, and the two copies compared byte for byte with `cmp`: identical). Tags were resolved to commits with `gh api repos/<org>/<repo>/git/ref/tags/<tag>`, and a second call for annotated tag objects. Line numbers were read off the fetched files. Every quoted string in the Chapters is listed in the tables below and was checked by a script that finds it inside the line range of its link (whitespace normalised, comment markers at the start of lines dropped) and that checks the range is tight: dropping its first or its last line loses a quote. The script also checks that the links in each Chapter and the links in the tables are the same set, and that each quoted string is in the Chapter's text. Where the source is markup, the quote column says what was dropped. Source types: 1 = source code, 2 = official documentation, 3 = standard or original paper, 4 = a post or talk by the system's own engineers. "Fetched by the agent, quote checked" is all that is claimed: no human has opened these links yet. They are listed in `docs/research/human-review-queue.md`.

## Observed, not cited

- **Reference Code.** Python, TypeScript (Node) and Go were run on every Test in the scope of each Problem before the content check. The Go binaries were built in the Sandbox image and run on the host.
- **The oracle.** The expected outputs of every Test come from a second implementation that uses other techniques (array-backed nodes, a strictly-increasing in-order check for `validate`, a persistent B-tree, parent pointers for `lca`, a token stack for `restore`), which agreed with the last Core Problem's Reference Code (`trees-save`) on 2,000 random command sequences in Python, 300 in TypeScript and 1,500 in Go. Sequences that insert into a tree or restore one leave out `lca`, because they can put a repeated value in the tree and the statement rules that out for `lca`. Every earlier Problem's Reference Code is a prefix of that file, run on its own Tests.
- **Largest Submit.** The Submit with the most hidden Tests is `trees-save`, the last Core Problem: 41 Tests, in two batches (25 and 16). The largest Extra Problem Submit is `trees-rightview`, 36 Tests. The limit is 50.

## Leads that changed

- Chapter 1 ("the binary tree and recursion on it") has no lead in the issue. A search for a real system whose recursion has a limit found SQLite's expression tree, with a per-node height and a depth limit.
- Chapters 2 and 3 split the issue's third entry ("a balanced tree in a real system, lead: Linux's red-black tree, database B-trees"). The red-black tree is read in Chapter 2, as the answer to why balance matters, and the B-tree in Chapter 3, with Rust's `BTreeMap` and SQLite's file format as the two systems.
- Chapter 4 reads the Go standard library's `io/fs.WalkDir` for depth-first and `bfs` for breadth-first. The issue names no system. The two are both directory walkers, so one Chapter reads both.
- Chapter 5 reads the flattened device tree's token stream for serialisation and `git merge-base` for the lowest common ancestor. Neither is a binary tree, and the Chapter says so: it reads the idea (begin and end markers, a depth counter, "better" common ancestors), not a binary tree.

## Outline entries folded into another Chapter

None: each of the issue's five outline entries has its own Chapter. Chapter 2 and Chapter 3 share the issue's third entry between them.

## Candidate Problems not in this Topic

None. All six fit the Build: Invert Binary Tree is the optional `mirror`; Maximum Depth of Binary Tree is `height`; Validate Binary Search Tree is `validate`; Level Order Traversal is `levels`; Serialize and Deserialize Binary Tree is `save` and `restore`. Lowest Common Ancestor of a BST is `lca`, written for any binary tree; the solution explains the shortcut a search tree allows.
