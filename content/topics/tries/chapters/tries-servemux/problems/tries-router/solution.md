A node of the router has a map for literal children, one slot for the wildcard child, and an optional value together with the list of wildcard names of the pattern that ends there. `handle` splits the pattern into segments, walks down creating the nodes it needs (every `{name}` goes to the single wildcard slot and its name goes on the list), and at the last node either prints `conflict` (a value is already there: the shapes are the same) or stores the value and the names.

`serve` is a depth-first search that follows the rule directly. At segment `i`, if the node has a literal child for it, search that child first. If the search returns a match, that is the answer. If it fails, go on to the wildcard child, if any, with the segment added to the captured list. When all segments have been used, a node that holds a value is a match, and any other node is a dead end. The first match found is the right one, because the search tries the literal before the wildcard at every position, from the left: that is exactly "a literal beats a wildcard at the first position where two patterns differ".

For `/a/b/c` with `/a/b/z` and `/a/{x}/c`, the search goes `a`, `b`, then needs `c` under `b` and finds only `z`, so that branch fails and the search returns to `a` to try the wildcard. This is the same literal-then-wildcard order as `matchPath` in Go's `routing_tree.go`.

Cost, for a path of S segments: `handle` takes O(S) expected time. `serve` takes O(S) when the first literal choices succeed, but in the **worst case** the search backs up at several levels and visits every node of the router once, O(N) node visits for N nodes (copying the captured segments at each wildcard step adds a factor of at most S). The Chapter gives the same bound for Go's search.
