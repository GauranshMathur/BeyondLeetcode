# Linux FIB: the longest matching route

A router holds a table of routes. Each route is a **prefix**, the first few bits of an address, and a place to send the packets whose address starts with those bits. Several routes can cover the same address, and the packet takes the most specific one: the **longest prefix** that matches. This Chapter reads the Linux kernel's IPv4 table at v6.6. The file that holds it, `net/ipv4/fib_trie.c`, describes itself as "IPv4 FIB: lookup engine and maintenance routines." ([net/ipv4/fib_trie.c, line 27](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L27)) It names its source: "This work is based on the LPC-trie which is originally described in:" ([line 12](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L12)), followed by a paper, "IP-address lookup using LC-tries." ([line 18](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L18))

## A prefix is the first n bits

Here a prefix is written `10.1.0.0/16`: an address, a slash and a length n, meaning the first n of its 32 bits. The route `10.0.0.0/8` covers every address whose first octet is 10, and `0.0.0.0/0` covers every address. The kernel refuses a prefix that has bits set after the first n. The check is `if ((plen < KEYLENGTH) && (key << plen))` ([line 1202](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1202)) and the message that goes with it is "Invalid prefix for given prefix length" ([line 1204](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1204)). `10.1.0.0/8` is refused for that reason, and Problem 3 prints `error` for it.

A lookup starts from the destination address as a number: `const t_key key = ntohl(flp->daddr);` ([line 1451](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1451)).

## A node reads a slice of the key

The kernel's notes describe two kinds of node. A **leaf** is "An end node with data. This has a copy of the relevant key, along with 'hlist' with routing table entries sorted by prefix length." ([Documentation/networking/fib_trie.rst, lines 10 to 11](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/networking/fib_trie.rst#L10-L11)) An inner node, a **tnode**, is "An internal node, holding an array of child (leaf or tnode) pointers, indexed through a subset of the key." ([lines 15 to 16](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/networking/fib_trie.rst#L15-L16))

That is the decision this Chapter is about: a node does not read one bit. The notes call it level compression: "instead of a pure binary tree, each internal node ("tnode") may contain an arbitrarily large array of links to several children." ([lines 42 to 43](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/networking/fib_trie.rst#L42-L43)) A node that reads k bits has a child array of 2^k entries, and a path of 32 bits needs at most 32 / k nodes (arithmetic). [Redis rax](/chapters/tries-rax) also lets a node hold many edges, but it cuts the key into bytes, where the kernel cuts it into slices of bits.

The second decision is to skip bits no route needs. The notes put it this way: "there will be some bits in the key skipped over because they represent a single path with no deviations. These "skipped bits" constitute Path Compression." ([lines 32 to 34](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/networking/fib_trie.rst#L32-L34)) A skipped bit is never compared on the way down, so the notes add what it costs: "Note that the search algorithm will simply skip over these bits when searching, making it necessary to save the keys in the leaves to verify that they actually do match the key we are searching for." ([lines 35 to 37](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/networking/fib_trie.rst#L35-L37)) rax also folds a chain with no deviations into one node, and it stores the skipped characters in that node ([src/rax.h, lines 57 to 61](https://github.com/redis/redis/blob/f60370ce28b946c1146dcea77c9c399d39601aaa/src/rax.h#L57-L61)). The kernel's node does not keep the skipped bits, which is why each leaf keeps its key.

## Go down, then back up

The lookup function labels its first loop: "Step 1: Travel to the longest prefix match in the trie" ([line 1470](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1470)). The loop can stop early, and the comment above its test says why: "we have a mismatch in skip bits and failed" ([line 1480](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1480)). The deepest node on the path is not always a match, so the next label is "Step 2: Sort out leaves and begin backtracing for longest prefix" ([line 1508](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1508)).

Backing up is done on the child index. The comment reads "If we are at cindex 0 there are no more bits for us to strip at this level so we must ascend back up one level to see if there are any more bits to be stripped there." ([lines 1535 to 1539](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1535-L1539)) and the step itself is `cindex &= cindex - 1;` under the comment "strip the least significant bit from the cindex" ([lines 1560 to 1561](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/net/ipv4/fib_trie.c#L1560-L1561)). Its effect on the number is arithmetic: it clears the lowest 1 bit of the index.

Take the routes `10.0.0.0/8` and `10.1.1.0/24`, and the address `10.1.2.3`. Going down follows the bits of 10, then 1, and then the third octet, 2, no longer agrees with the /24 route. The answer is the /8 route that the walk passed on the way, so the lookup has to get back to it. This is the Chapter's own example, worked by hand.

Problem 3 uses one bit per node and skips none. Each route sits at the depth of its length, so a lookup can note the last route it meets while going down and needs no climb. That is a choice of this Build, not the kernel's. It is also why the Build has a clear bound: a lookup takes at most 32 steps, the same in the **worst case** with ten routes or a million, because a step is a bit of the address and not a route.

## What the Build leaves out

The kernel's leaf holds "routing table entries sorted by prefix length" ([Documentation/networking/fib_trie.rst, lines 10 to 11](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/networking/fib_trie.rst#L10-L11)), and the Build keeps one value per prefix. The Build has no level compression, skips no bits, and handles IPv4 only.
