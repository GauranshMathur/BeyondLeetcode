# PostgreSQL: two rows of the table are enough

The edit distance between two words is the least it costs to turn one into the other by inserting, deleting and substituting letters. PostgreSQL's `fuzzystrmatch` module offers it as `levenshtein(source text, target text, ins_cost int, del_cost int, sub_cost int)`, and its documentation says "The cost parameters specify how much to charge for a character insertion, deletion, or substitution, respectively." ([doc/src/sgml/fuzzystrmatch.sgml, lines 262 to 272](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/doc/src/sgml/fuzzystrmatch.sgml#L262-L272); the markup dropped) The module's C function passes the two words and the three costs to `varstr_levenshtein` ([contrib/fuzzystrmatch/fuzzystrmatch.c, lines 168 to 169](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/contrib/fuzzystrmatch/fuzzystrmatch.c#L168-L169)), which is defined in `src/backend/utils/adt/levenshtein.c` ([lines 73 to 77](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L73-L77)). This Chapter reads that file in PostgreSQL 17.0, the tag `REL_17_0`, the commit `d7ec59a`.

## The table, as the comment describes it

The file's comment describes the table like the ones in the earlier Chapters: "One way to compute Levenshtein distance is to incrementally construct an (m+1)x(n+1) matrix where cell (i, j) represents the minimum number of operations required to transform the first i characters of s into the first j characters of t. The last column of the final row is the answer." ([src/backend/utils/adt/levenshtein.c, lines 40 to 44](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L40-L44); the comment markers dropped) Here `m` is the length of the source word and `n` of the target ([lines 108 to 109](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L108-L109)). The comment then says what the code does instead: "We use that algorithm here with some modification. In lieu of holding the entire array in memory at once, we'll just use two arrays of size m+1 for storing accumulated values. At each step one array represents the "previous" row and one is the "current" row of the notional large array." ([lines 46 to 50](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L46-L50); the comment markers dropped) The code allocates both at once and points the second at the half after the first: `prev = (int *) palloc(2 * m * sizeof(int)); curr = prev + m;` ([lines 212 to 213](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L212-L213); `m` was raised by one on [line 208](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L208), so each array holds the `m + 1` cells of the comment).

## Filling a row from the one before

Each cell of the current row is the cheapest of three moves, and the code for one cell is:

```c
/* Calculate costs for insertion, deletion, and substitution. */
ins = prev[i] + ins_c;
del = curr[i - 1] + del_c;
sub = prev[i - 1] + ((*x == *y) ? 0 : sub_c);

/* Take the one with minimum cost. */
curr[i] = Min(ins, del);
curr[i] = Min(curr[i], sub);
```

([lines 312 to 319](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L312-L319); indentation reduced) Read them against the comment. `prev[i]` is the cell for the same prefix of the source and one letter fewer of the target, so reaching the current cell from it inserts a letter. `curr[i - 1]` is one letter fewer of the source in the same row, so reaching the current cell deletes one. `prev[i - 1]` is one letter fewer of both, so the move substitutes, and costs nothing when the two letters are equal (`*x == *y`). A cell reads two cells of the row before and one of its own row, and nothing older. The outer loop goes over the letters of the target, `for (y = target, j = 1; j < n; j++)` ([line 223](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L223)), and at the end of each row: "Swap current row with previous row." with `temp = curr; curr = prev; prev = temp;` ([lines 326 to 329](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L326-L329); the comment marker dropped and the three statements shown on one line). The answer ends up where the last swap put it: "Because the final value was swapped from the previous row to the current row, that's where we'll find it." ([lines 397 to 398](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L397-L398); the comment markers dropped), `return prev[m - 1];` ([line 400](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L400)).

## Two rows, and what they cost

The function states the saving itself: "(This implementation uses O(m) memory and has O(mn) complexity.)" ([lines 121 to 122](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L121-L122)). The time is O(m × n) in the **worst case**, one step per cell, and the space is the two rows, O(m), where a whole table would be O(m × n). The comment above that check says why it limits its input: "For security concerns, restrict excessive CPU+RAM usage." ([lines 121 to 122](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L121-L122)). It refuses a word longer than `MAX_LEVENSHTEIN_STRLEN` ([line 26](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L26), 255) unless the caller is trusted ([lines 127 to 133](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L127-L133)), and the documentation says the same: "Both source and target can be any non-null string, with a maximum of 255 characters" ([lines 269 to 270](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/doc/src/sgml/fuzzystrmatch.sgml#L269-L270); the markup dropped). With that cap a call fills at most 255 × 255 = 65,025 cells (arithmetic).

Two rows are enough because of the three moves. The previous Topic's [git Chapter](/chapters/dp-1d-git) read a function that keeps three rows, because it has a fourth move, a swap, that reaches two rows back, and its comment says two rows would do if a swap cost as much as a deletion plus an insertion, or more. PostgreSQL's three moves reach back one row. What the two rows give up is the way back: when the third row is written, the first is gone, so nothing can be walked back as in [Hunspell](/chapters/dp-2d-hunspell), [liblqr](/chapters/dp-2d-liblqr) or [PyTorch](/chapters/dp-2d-pytorch), where the source's own comment about the whole table says "this memory can be optimized with sliding window trick + Hirschberg trick" ([knapsack.py, lines 82 to 83](https://github.com/pytorch/pytorch/blob/134179474539648ba7dee1317959529fbd0e7f89/torch/_functorch/_activation_checkpointing/knapsack.py#L82-L83); the comment markers dropped). The distance is a single number, and a single number needs no path.

## Giving up early

The file is included twice, the second time to define a version that takes a maximum distance of interest ([lines 8 to 11](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L8-L11)), `levenshtein_less_equal`. Its documentation: "levenshtein_less_equal is an accelerated version of the Levenshtein function for use when only small distances are of interest. If the actual distance is less than or equal to max_d, then levenshtein_less_equal returns the correct distance; otherwise it returns some value greater than max_d." ([doc/src/sgml/fuzzystrmatch.sgml, lines 277 to 281](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/doc/src/sgml/fuzzystrmatch.sgml#L277-L281); the markup dropped) The code keeps only part of each row, "a start_column and stop_column that identify the portion of the matrix close to the diagonal which can still affect the final answer" ([levenshtein.c, lines 62 to 64](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L62-L64); the comment markers dropped), and when the two columns cross it stops: "If they cross, we're going to exceed the bound." with `return max_d + 1;` ([lines 389 to 391](https://github.com/postgres/postgres/blob/d7ec59a63d745ba74fba0e280bbf85dc6d1caa3e/src/backend/utils/adt/levenshtein.c#L389-L391); the comment marker dropped). The Extra Problem asks for the simplest form of the idea. If every cell of a finished row is already over the limit, the answer is too, because each cell of the next row is built from a cell of this one or of its own row by adding a cost that is not negative. The worst case does not improve, it is still O(m × n); an answer that is far over the limit is found after fewer rows.

## What the Problems build

`edit INS DEL SUB` prints the cheapest cost of turning the first word into the second, with those costs for inserting, deleting and substituting a letter, using two rows. The Extra Problem `within INS DEL SUB LIMIT` prints that cost if it is at most the limit, and `over` if not.
