The question "do the piles finish within `H` hours at rate `R`?" has a single flip: if it is true at `R`, it is true at every larger rate, because a higher rate never takes more hours for any pile. So the answer is the first `R` where the test turns true, and you can search for it the way you searched for the first bad commit. The range of candidates is `1..max(pile)`: the top is always enough, and the bottom is the smallest rate allowed.

Write the test as a function `hours(R) = sum(ceil(p / R))`, with the ceiling done in integers, for example `(p + R - 1) / R`. Keep `low = 1` and `high = max(pile)`, and while `low < high`: take `m = mid(low, high)`; if `hours(m) <= H`, then `m` works and a smaller rate may too, so `high = m`; otherwise `low = m + 1`. The invariant is that the answer is in `low..high`.

Each test is one pass over the `n` piles, and there are at most `ceil(log2(max pile))`, about 30, tests, so the **worst case** is `O(n log M)` for `n` piles and biggest pile `M`, with constant extra space. The hours can reach 5,000 x 1,000,000,000 = 5 x 10^12, which does not fit in 32 bits; Go's `int` and Python's integers are fine, and in TypeScript every number up to 2^53 is exact. Searching the rate by trying `1, 2, 3, ...` would take up to a billion tests of 20,000 piles each.
