Keep `lo = 0` and `total = 0`. For each index `hi` from 0: add `values[hi]` to `total`. While `total > W`, subtract `values[lo]` and add one to `lo`. Then `hi - lo + 1` is the longest run ending at `hi` that fits; keep the largest.

**Why it is right.** Claim: after the inner loop, `lo` is the smallest start such that `values[lo..hi]` fits. The sizes are positive, so a run that fits still fits when you drop items from its left, and a run that does not fit cannot be fixed by adding items to its right. If `values[lo..hi]` did not fit at some earlier `hi`, no later run that starts at or before `lo` can fit either, so `lo` never needs to move back. If a single item is bigger than `W`, the loop removes everything including that item, the window is empty and `hi - lo + 1` is 0.

**Cost.** `hi` moves right n times and `lo` moves right at most n times, since it never passes `hi + 1`. So the loop does at most 2n steps: O(n) in the **worst case**, which is also amortised O(1) per item for the inner loop even though one item can drop many. Extra space is O(1). Starting a fresh run at every position is O(n²) in the worst case, and the largest Hidden Test has thousands of items.
