`drop` is the cheapest way to cancel: it sets a flag on the item, takes its ID out of the map of queued timers and adds one to the count of dropped items in the array. The heap itself is untouched, so the heap order is still valid, and dropped items sit in the array until a clean-up removes them.

The clean-up runs at the start of `advance`. When the array holds more than 100 items and more than half are dropped, it rebuilds: it copies the items that are not dropped, in array order, and runs the `init` of Problem 3 on them, which is O(n) comparisons in the **worst case**. Otherwise it pops dropped items off the top, which is O(log n) comparisons each in the **worst case**. While `advance` fires timers, a dropped item that reaches the top is removed and skipped.

Cost: `drop` is O(1) in the **worst case**. A rebuild is O(n), but it happens only when more than half of more than 100 items are dropped, so the O(n) pays for more than n / 2 earlier drops: O(1) **amortised** per drop. A dropped item is also removed by a pop at most once, O(log n) in the **worst case**. The space cost is that dropped items stay in memory until a clean-up reaches them: at most half the array once it holds more than 100 items, and any number below that.
