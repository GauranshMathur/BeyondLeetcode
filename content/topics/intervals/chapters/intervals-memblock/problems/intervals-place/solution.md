Keep the merged intervals in a list sorted by `lo`, with a counter `covered` of the numbers they hold. To place `lo hi`: binary-search the first merged interval whose `hi` is at least `lo - 1`; call its index `i`. Walk forward from `i` while an interval starts at `hi + 1` or earlier. Each one touches the new interval, so widen the new interval to include it and subtract its size from `covered`. Then replace the walked intervals with the one new interval and add its size to `covered`. Print the length of the list and `covered`. `add` does the same without printing, and `merged` prints the list.

**Why it is right.** The list is in order and none of its intervals touch, so the ones that end before `lo - 1` are all before the first that can touch. Their ends rise along the list, which is what lets the binary search work. Walking on, the intervals that start at `hi + 1` or earlier are the ones that touch; the first one that starts later, and everything after it, is out of reach. After the replacement the list is again in order with no touching pair.

**Cost.** The search is O(log n) in the **worst case**. Replacing the walked intervals shifts the later part of the list, which is O(n) in the **worst case**. Each interval that is absorbed leaves the list and was added once, so over a whole run the absorbing steps are O(1) amortised per `place`. One `place` is O(n) in the **worst case**, and a run of n of them O(n²) in the **worst case**, though a shift of a list is fast in practice. Sorting and merging all the intervals again on every `place` would be O(n log n) each.
