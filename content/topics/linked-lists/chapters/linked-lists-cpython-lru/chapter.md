# CPython: the list and the table behind lru_cache

A cache that keeps the last N things needs two operations to be fast: find an entry by its key, and move an entry to "most recent" or drop the "least recent". A hash table does the first and a doubly linked list does the second. This Chapter reads the one CPython 3.13.0 builds for `functools.lru_cache` in `Modules/_functoolsmodule.c` (commit `60403a5`), and then the decision Redis made not to build it.

## What it stores

The documentation describes the decorator: it wraps a function "with a memoizing callable that saves up to the maxsize most recent calls", and says "An LRU (least recently used) cache works best when the most recent calls are the best predictors of upcoming calls". ([functools, Python 3.13](https://docs.python.org/3.13/library/functools.html#functools.lru_cache)) In C, each cached call is a link in a list: ([Modules/_functoolsmodule.c, lines 814 to 819](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L814-L819))

```c
typedef struct lru_list_elem {
    PyObject_HEAD
    struct lru_list_elem *prev, *next;  /* borrowed links */
    Py_hash_t hash;
    PyObject *key, *result;
} lru_list_elem;
```

and the cache object holds `lru_list_elem root;` (the head of the ring from Chapter 1, itself a link), `PyObject *cache;` (a dict), and the counters `hits`, `misses` and `maxsize`. ([lines 847 to 862](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L847-L862)) The dict maps a key to its link, so a lookup returns the node itself: `link = _PyDict_GetItem_KnownHash(self->cache, key, hash);`. ([line 1051](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1051)) That is the whole point of putting a list node in a table. The table finds the node in expected O(1), as the [Hash tables Topic](/chapters/hash-tables-cpython-dict) shows for CPython's dict, and since the node holds both neighbours, the list can unlink it with no walk, as in Chapters 1 and 2.

The list is ordered by recency. Three helpers handle it: `lru_cache_extract_link` unlinks a node by joining its neighbours, `lru_cache_append_link` inserts it just before the root, and `lru_cache_prepend_link` just after. ([lines 976 to 1003](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L976-L1003)) Because new entries are appended before the root, the **newest** is `root->prev` and the **oldest** is `root->next`.

## A hit, a miss, and a full cache

On a hit the code finds the link, extracts it, appends it, counts a hit, and returns the stored result: `lru_cache_extract_link(link); lru_cache_append_link(self, link);` then `self->hits++`. ([lines 1051 to 1059](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1051-L1059)) The result returned is the one stored in the link, not a new one, so the function is not called again. On a miss it counts a miss (`self->misses++`), calls the function ([lines 1065 to 1066](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1065-L1066)) and, if the cache has room (`PyDict_GET_SIZE(self->cache) < self->maxsize`), makes a new link, stores it in the dict and appends it. ([lines 1092 to 1119](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1092-L1119))

When the cache is full, it does not free one link and allocate another. The comment says: "Rather than free the old link and allocate a new one, we reuse the link for the new key and result and move it to front of the cache to mark it as recently used." ([lines 1121 to 1124](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1121-L1124)) The code takes the oldest, `link = self->root.next;`, extracts it, and pops its key from the dict ([lines 1136 to 1143](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1136-L1143)); overwrites its `hash`, `key` and `result` ([lines 1175 to 1177](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1175-L1177)); stores the same link in the dict under the new key; and appends it ([lines 1183 to 1194](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1183-L1194)). (The comment says "front"; the call is `lru_cache_append_link`, which puts the link at the newest end. The Build follows the code.) So a miss in a full cache does one eviction and no allocation. Each call does a constant number of list operations, which are O(1) in the **worst case**, and a constant number of dict operations, which are O(1) **expected**, so a call is O(1) expected.

Two more cases appear in the code. The constructor picks a different wrapper by `maxsize`: a negative size becomes 0, and 0 selects `uncached_lru_cache_wrapper` ([lines 1236 to 1246](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1236-L1246)), which only counts a miss and calls the function. ([lines 925 to 935](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L925-L935)) And the statistics: `cache_info` returns `hits`, `misses`, `maxsize` and the dict's size ([lines 1353 to 1366](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1353-L1366)), the documentation's "hits, misses, maxsize and currsize"; `cache_clear` ("Clear the cache and cache statistics") sets `hits = misses = 0` and clears the dict and the list. ([lines 1368 to 1385](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Modules/_functoolsmodule.c#L1368-L1385))

## The counter-example: Redis keeps no list

Redis, the key-value server, evicts the least recently used keys when it is full, and does not keep the list. Its source says: "Redis uses an approximation of the LRU algorithm that runs in constant memory. Every time there is a key to expire, we sample N keys (with N very small, usually in around 5)", and it evicts the best of those. ([src/evict.c, lines 102 to 107, Redis 7.2.0](https://github.com/redis/redis/blob/29622276ecd7b74312798e6772744858a8a6f9bf/src/evict.c#L102-L107)) Each object carries a 24-bit field, `unsigned lru:LRU_BITS;` with `#define LRU_BITS 24`, holding its last access time. ([src/server.h, line 892](https://github.com/redis/redis/blob/29622276ecd7b74312798e6772744858a8a6f9bf/src/server.h#L892) and [lines 899 to 905](https://github.com/redis/redis/blob/29622276ecd7b74312798e6772744858a8a6f9bf/src/server.h#L899-L905)) Compare the cost per key: two pointers for a list node, against 24 bits. The price is that the eviction is approximate: it picks the best of a sample, not the true oldest. The reasoning the source gives is the one in the comment, "constant memory"; this Chapter reads no benchmark. The Problems build CPython's exact version.

## What the Problems build

The memory and the ring of the earlier Chapters stay. The cache's nodes are four cells: `next`, `prev`, a key and a result. The lookup from key to node is the built-in map of your language (a Python `dict`, a TypeScript `Map`, a Go `map`): the Build here is a separate program from the table you wrote in the Hash tables Topic, so the map is the one the language gives. The first Problem is the hit, miss and eviction rules, with `order` to look at the list. The second adds the statistics, `clear`, and a cache of size 0.
