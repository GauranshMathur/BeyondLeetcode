# Linux: noticing that a list is broken

A list that has gone wrong is hard to see from the inside. The [Two pointers Topic](/chapters/two-pointers-emacs-cycles) reads how Emacs notices that a singly linked list never ends: it walks with a second pointer, because a chain of one-way links gives no other evidence. This Chapter reads the other answer, in Linux 6.6 (commit `ffc2532`). The ring of Chapter 1 stores every link twice, as `a->next == b` and `b->prev == a`, and the kernel checks that the two agree.

## Check the neighbours before you write

The code lives in `lib/list_debug.c`, whose header says it holds "the linked list validation and error reporting for LIST_HARDENED and DEBUG_LIST", and whose first comment gives the reason: "Failures here indicate memory corruption (and possibly an exploit attempt)." ([lib/list_debug.c, lines 1 to 19](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/lib/list_debug.c#L1-L19))

Before linking a node between `prev` and `next`, `__list_add_valid_or_report` tests, in this order: `prev` is `NULL`; `next` is `NULL`; `next->prev != prev`; `prev->next != next`; and `new == prev || new == next`, the report for which is "list_add double add". ([lines 21 to 41](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/lib/list_debug.c#L21-L41)) The second and third are the doubled link: both neighbours must agree that they are neighbours. For removal, `__list_del_entry_valid_or_report` tests: `next` is `NULL`; `prev` is `NULL`; `next == LIST_POISON1`; `prev == LIST_POISON2`; `prev->next != entry`; `next->prev != entry`. ([lines 44 to 71](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/lib/list_debug.c#L44-L71)) The poison tests are the payoff of Chapter 1's poison: a second `list_del` of the same node finds `LIST_POISON1` in its `next`, and is refused instead of writing through a bad address.

The checks are called from the ring functions of Chapter 1. `__list_add` begins `if (!__list_add_valid(new, prev, next)) return;`, so a failed check skips the four writes. ([lines 146 to 157](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/include/linux/list.h#L146-L157)) `__list_del_entry` does the same before `__list_del`. ([lines 213 to 219](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/include/linux/list.h#L213-L219)) One detail follows from the code of `list_del`: it calls `__list_del_entry(entry)` and then writes the two poison values with no condition ([lines 227 to 232](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/include/linux/list.h#L227-L232)), so the node is poisoned even when the check refused to unlink it. Likewise `list_del_init` re-initialises the node whether or not the check passed ([lines 285 to 289](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/include/linux/list.h#L285-L289)).

The checks are a choice, not free. They are compiled in only under a configuration option: `#ifdef CONFIG_LIST_HARDENED` opens the real functions ([line 41](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/include/linux/list.h#L41)), and the `#else` branch defines both validators as functions that return `true` ([lines 127 to 138](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/include/linux/list.h#L127-L138)). The Kconfig help for `DEBUG_LIST` says it "trades better quality error reports for performance, and is more suitable for kernel debugging. If you care about performance, you should only enable CONFIG_LIST_HARDENED instead." ([lib/Kconfig.debug, lines 1679 to 1689](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/lib/Kconfig.debug#L1679-L1689)) `LIST_HARDENED` is described as "Minimal integrity checking in the linked-list manipulation routines to catch memory corruptions that are not guaranteed to result in an immediate access fault." ([security/Kconfig.hardening, lines 284 to 291](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/security/Kconfig.hardening#L284-L291)) Each check is a constant number of reads of the two neighbours, so the cost per `list_add` or `list_del` stays O(1) in the **worst case**.

## What a check proves, and what it does not

These checks look at one operation's neighbours. They do not walk the list, and nothing in the file above does. The Build adds a whole-list walk of its own, and it is worth seeing why it can be simple. This is an argument, not a claim about the kernel.

Walk from the head, and at each step from `cur` to `nxt` check that `nxt`'s `prev` is `cur`. Suppose the walk visits `v0` (the head), `v1`, `v2`, and so on, and every step passes the check. Suppose some node repeats: `v_j == v_i` with `i < j`. Their `prev` fields are `v_(j-1)` and `v_(i-1)`, and one node has one `prev`, so `v_(j-1) == v_(i-1)`. Repeat that argument and it reaches `v_(j-i) == v_0`, the head. So the first node to repeat is always the head itself: the walk never visits another node twice. With a finite number of nodes it must therefore end, at the head, at a failed check, or at a `NULL`. It cannot circle forever among other nodes, and it needs no second pointer. A chain with only `next` links has no `prev` to compare, which is why the Emacs Chapter needed two pointers. The check costs O(n) in the **worst case**, one visit per node, with O(1) extra space.

## What the Problems build

The first Problem makes the commands of Chapters 1 and 2 safe: `add`, `add_tail`, `del` and `del_init` run the checks above, in the same order, and report the first failure. The second Problem is the whole-list walk, `check`, which reports where the doubled links stop agreeing.
