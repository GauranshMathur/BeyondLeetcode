Sort the jobs by deadline. Keep a max-heap `kept` of run times and `clock = 0`. For each job in order: push its run time, add it to `clock`; if `clock` is greater than the job's deadline, pop the largest run time from `kept` and subtract it from `clock`. Print the size of `kept`.

**Why it is right.** A set of jobs can all meet their deadlines if and only if running them in order of deadline does (the exchange argument of `edf`). So the question is which subset to keep, with the deadlines in sorted order. After handling the first `i` jobs, the rule keeps the most jobs among those `i` that can still meet their deadlines, and among all sets of that size it keeps the one with the smallest total run time. When job `i + 1` arrives and everything kept plus it does not fit, some job has to go. Going without the longest of the kept jobs and the new one leaves the set with the most room, since any other choice leaves a larger total, and the count is the same. Having the least total at every size never hurts a later job, which only needs total time to be small.

**Cost.** Sorting is O(n log n) in the **worst case**; each job is pushed once and popped at most once, each O(log n) in the **worst case**, so O(n log n) overall with O(n) extra space.
