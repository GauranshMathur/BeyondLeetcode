# Walking a tree: Go goes deep, bfs goes wide

A **traversal** visits every node of a tree once. The order it uses is a design decision, because different orders suit different jobs and cost different amounts of memory. There are two families. A **depth-first** walk follows one branch all the way down before it tries the next, and recursion does that for free. A **breadth-first** walk visits the nodes level by level, from the root outwards. A directory tree is a tree with many children per node instead of two, and two tools that walk it make the opposite choices: the `io/fs` package of Go (1.22.0) and `bfs` (4.1.4), a variant of the Unix `find` command.

## Go: visit the directory, then read it, then go in

`fs.WalkDir` is the standard way to go through a directory tree in Go. Its documentation gives the contract: "WalkDir walks the file tree rooted at root, calling fn for each file or directory in the tree, including root." ([src/io/fs/walk.go, lines 105 to 106](https://github.com/golang/go/blob/a10e42f219abb9c5bc4e7d86d9464700a42c7d57/src/io/fs/walk.go#L105-L106)) It calls `fn` once for each entry, so a walk costs O(n) calls in the **worst case**, where n is the number of files and directories.

The recursive function that does the work shows the order. It calls the callback on the directory first: `if err := walkDirFn(name, d, nil); err != nil || !d.IsDir() {`. ([src/io/fs/walk.go, line 73](https://github.com/golang/go/blob/a10e42f219abb9c5bc4e7d86d9464700a42c7d57/src/io/fs/walk.go#L73)) Only then does it read the directory, `dirs, err := ReadDir(fsys, name)`, ([src/io/fs/walk.go, line 81](https://github.com/golang/go/blob/a10e42f219abb9c5bc4e7d86d9464700a42c7d57/src/io/fs/walk.go#L81)) and recurse into each child: `for _, d1 := range dirs {` and `if err := walkDir(fsys, name1, d1, walkDirFn); err != nil {`. ([src/io/fs/walk.go, lines 93 to 95](https://github.com/golang/go/blob/a10e42f219abb9c5bc4e7d86d9464700a42c7d57/src/io/fs/walk.go#L93-L95)) A node is handled before its children. That order is called **pre-order**.

The order is not an accident, because it makes pruning possible. The documentation says the callback is called early on purpose: "The function is called before reading a directory, to allow SkipDir or SkipAll to bypass the directory read entirely or skip all remaining files and directories respectively." ([src/io/fs/walk.go, lines 64 to 66](https://github.com/golang/go/blob/a10e42f219abb9c5bc4e7d86d9464700a42c7d57/src/io/fs/walk.go#L64-L66); the source writes the two names as links, shown here without the brackets) The special value `SkipDir` is "to indicate that the directory named in the call is to be skipped". ([src/io/fs/walk.go, lines 12 to 13](https://github.com/golang/go/blob/a10e42f219abb9c5bc4e7d86d9464700a42c7d57/src/io/fs/walk.go#L12-L13)) A callback that refuses a whole subtree never makes the walk pay for reading it. A walk that visited children first could not do that.

The walk also fixes the order of the children, and says what it costs: "The files are walked in lexical order, which makes the output deterministic but requires WalkDir to read an entire directory into memory before proceeding to walk that directory." ([src/io/fs/walk.go, lines 111 to 113](https://github.com/golang/go/blob/a10e42f219abb9c5bc4e7d86d9464700a42c7d57/src/io/fs/walk.go#L111-L113))

A binary tree has two children, and a depth-first walk of one has three natural orders, depending on when the node is handled. **Pre-order** handles it before both children, as `WalkDir` does. **In-order** handles it between its left and its right child. **Post-order** handles it after both. On a search tree, in-order gives the values in increasing order, which follows from the search rule in the last Chapter. In the Problem `walk` you write all three with one recursive function.

## bfs: shallowest first

`bfs` makes the other choice. The project describes itself in its first sentence: "`bfs` is a variant of the UNIX `find` command that operates breadth-first rather than depth-first." ([README.md, line 30](https://github.com/tavianator/bfs/blob/465ac7ae544464f17d7a2dfcb993326ab2f00536/README.md#L30); the source has links and code marks on some words, dropped here) Its README gives the reason with an example, a directory `haystack` with one very deep branch called `deep` and, beside it, a shallow branch with a file `needle` in it ([README.md, lines 58 to 70](https://github.com/tavianator/bfs/blob/465ac7ae544464f17d7a2dfcb993326ab2f00536/README.md#L58-L70)): "`find` will explore the entire `deep` directory tree before it ever gets to the `shallow` one that contains what you're looking for. On the other hand, `bfs` lists files from shallowest to deepest, so you never have to wait for it to explore an entire unrelated subtree." ([README.md, lines 72 to 73](https://github.com/tavianator/bfs/blob/465ac7ae544464f17d7a2dfcb993326ab2f00536/README.md#L72-L73); code marks dropped) The README states the gain in the weaker form that fits: breadth-first "typically finds the file(s) you're looking for faster". ([README.md, line 54](https://github.com/tavianator/bfs/blob/465ac7ae544464f17d7a2dfcb993326ab2f00536/README.md#L54); the source writes the program name inside an HTML code tag, dropped here)

The order is the nodes of depth 0, then of depth 1, then of depth 2, and so on. A **level** is all the nodes at the same depth. To visit them in that order you keep a **queue**: take a node from the front, visit it, and put its children at the back. The queue holds one level and part of the next at any moment, so it needs O(w) space in the **worst case**, where w is the width of the widest level. A depth-first walk with recursion needs space for one call per level on the current path, O(h) for height h, so the two walks suit different shapes: a long thin tree is cheap for breadth-first and costly for depth-first, and a wide shallow one is the reverse. Both visit every node once, O(n) time in the **worst case**. These costs are arithmetic on the descriptions above.

In the Problem `levels` you print a tree one level per line, shallowest first. In the optional Problem `rightview` you use the same walk to see the tree as if from the right.
