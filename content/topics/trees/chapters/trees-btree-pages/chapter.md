# B-trees: fewer, fatter nodes

A balanced binary tree keeps its height small, but each node holds one key, so a path from the root to a key still passes through about log₂ n nodes. A **B-tree** keeps the same search rule and the same balance and changes the node: it holds several sorted keys, and a node with N keys has N + 1 children, one for each gap between keys and one at each end. This Chapter reads two B-trees, the standard library's ordered map in Rust (1.82.0) and the file format underneath SQLite (3.46.0), and the reason each gives for wider nodes. They give different reasons.

## Rust: the cost is allocations and cache misses

The documentation of `BTreeMap` starts from the case against a binary search tree. It grants that a perfectly balanced one "performs the theoretical minimum amount of comparisons necessary to find an element", and then names the cost: "every element is stored in its own individually heap-allocated node. This means that every single insertion triggers a heap-allocation, and every single comparison should be a cache-miss." ([library/alloc/src/collections/btree/map.rs, lines 45 to 49](https://github.com/rust-lang/rust/blob/f6e511eec7342f59a25f7c0534f1dbea00d01b14/library/alloc/src/collections/btree/map.rs#L45-L49))

Its answer is the wider node: "A B-Tree instead makes each node contain B-1 to 2B-1 elements in a contiguous array. By doing this, we reduce the number of allocations by a factor of B, and improve cache efficiency in searches. However, this does mean that searches will have to do more comparisons on average." ([library/alloc/src/collections/btree/map.rs, lines 53 to 55](https://github.com/rust-lang/rust/blob/f6e511eec7342f59a25f7c0534f1dbea00d01b14/library/alloc/src/collections/btree/map.rs#L53-L55); the source writes *more* between asterisks, shown here without them) The documentation says how many: "Using linear search, searching for a random element is expected to take B * log(n) comparisons, which is generally worse than a BST." ([library/alloc/src/collections/btree/map.rs, lines 64 to 65](https://github.com/rust-lang/rust/blob/f6e511eec7342f59a25f7c0534f1dbea00d01b14/library/alloc/src/collections/btree/map.rs#L64-L65)) That is an **expected** count, and the trade is stated plainly: more comparisons, fewer allocations and fewer cache misses.

The number B is a constant in the source: `const B: usize = 6;`, `pub const CAPACITY: usize = 2 * B - 1;` and `pub const MIN_LEN_AFTER_SPLIT: usize = B - 1;`. ([library/alloc/src/collections/btree/node.rs, lines 42 to 44](https://github.com/rust-lang/rust/blob/f6e511eec7342f59a25f7c0534f1dbea00d01b14/library/alloc/src/collections/btree/node.rs#L42-L44)) A node holds up to 11 keys and, after a split, no fewer than 5.

## How a full node splits

A tree that grows by adding keys to full nodes has to make room. The source comment on the split says how: "The goal of the split point is for its key and value to end up in a parent node; the keys, values and edges to the left of the split point become the left child; the keys, values and edges to the right of the split point become the right child." ([library/alloc/src/collections/btree/node.rs, lines 892 to 894](https://github.com/rust-lang/rust/blob/f6e511eec7342f59a25f7c0534f1dbea00d01b14/library/alloc/src/collections/btree/node.rs#L892-L894)) That is the shape of a split: one overfull node becomes two nodes and one key to hand upwards. The Problem `btree` uses the same shape with B = 2. A node holds at most 3 keys, which is `CAPACITY` for B = 2, and a fourth key makes it split, with `MIN_LEN_AFTER_SPLIT` = B - 1 = 1 key staying in the left node. The Problem adds the rule for the rest: if the parent overflows it splits the same way, and a root that splits gets a new root with one key above it. That is the only way the tree gets taller, and it happens at the root, so all leaves always stay at the same depth.

The height of this small B-tree is O(log n) in the **worst case**. Every node but the root keeps at least 1 key, so every internal node has at least 2 children, and level d (the root is level 0) has at least 2^d nodes with at least 1 key each. A tree of h levels therefore holds at least 2^h - 1 keys, so h is at most log₂(n + 1). With at most 3 keys and 4 children per node, level d has at most 4^d nodes, so h is at least log₄(n + 1). That is arithmetic on the rule above. Adding a key is one walk down plus at most one split per level on the way back, and each split is constant work because a node never holds more than 4 keys, so adding is O(log n) in the **worst case** too.

## SQLite: the cost is reading pages from disk

SQLite's B-tree has the same shape for another reason. The comment at the top of its B-tree code says: "The basic idea is that each page of the file contains N database entries and N+1 pointers to subpages." ([src/btreeInt.h, lines 19 to 20](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/btreeInt.h#L19-L20)) The order rule is the one from the search tree: "All of the keys on the page that Ptr(0) points to have values less than Key(0). All of the keys on page Ptr(1) and its subpages have values greater than Key(0) and less than Key(1)." ([src/btreeInt.h, lines 26 to 28](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/btreeInt.h#L26-L28)) And the cost it counts is pages: "Finding a particular key requires reading O(log(M)) pages from the disk where M is the number of entries in the tree." ([src/btreeInt.h, lines 32 to 33](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/btreeInt.h#L32-L33)) A node is a page of the file, and the page size is chosen by the file: "The page size can be any power of 2 between 512 and 65536." ([src/btreeInt.h, line 49](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/btreeInt.h#L49))

SQLite counts the cost of a lookup in pages read. The more entries a page holds, the fewer levels the tree has, so the fewer pages a lookup reads (arithmetic: with N entries per page the height is about log base N of M). Rust counts allocations and cache misses instead, and the structure each chose is the same.

## What the Problems build

`bt` is a second structure in the program, beside the binary tree, and the two do not touch. `bt add` adds keys to a B-tree whose nodes hold at most 3 keys and splits as described above. `bt show` prints it a level at a time. `bt find` reports how many nodes the search read, to set against the nodes `find` visited in the search tree: a chain of 200 keys takes 200 visits, and a B-tree of the same 200 takes a handful of reads.
