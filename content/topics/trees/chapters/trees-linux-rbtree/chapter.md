# Binary search trees: why the kernel balances them

A **binary search tree** is a binary tree with one extra rule: every value in a node's left subtree is smaller than the node's value, and every value in its right subtree is larger. The rule turns the tree into a sorted collection. To look something up you start at the root, compare, and go left or right, which is the same idea as binary search on a sorted array, except that each step follows a link instead of halving an index range. This Chapter reads the red-black tree in the Linux kernel (v6.6), a search tree that keeps itself balanced, and what the kernel's documentation and code say about why it must.

## Search and insert are a loop

The kernel's documentation describes the search in one sentence: "Writing a search function for your tree is fairly straightforward: start at the root, compare each value, and follow the left or right branch as necessary." ([Documentation/core-api/rbtree.rst, lines 81 to 82](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L81-L82)) Its example is a `while (node)` loop that compares and moves: `if (result < 0) node = node->rb_left; else if (result > 0) node = node->rb_right; else return data;`. ([Documentation/core-api/rbtree.rst, lines 96 to 101](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L96-L101)) The loop does one comparison per node on the path, so a search costs O(h) in the **worst case**, where h is the height of the tree. This is the Problem `find`, which also reports how many nodes the search looked at.

Insertion is the same walk, ending at an empty child: "Inserting data in the tree involves first searching for the place to insert the new node, then inserting the node and rebalancing ("recoloring") the tree." ([Documentation/core-api/rbtree.rst, lines 109 to 110](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L109-L110)) A key that is already in the tree is not inserted: the example's loop ends with `else return FALSE;`. ([Documentation/core-api/rbtree.rst, lines 132 to 133](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L132-L133)) The Problem `insert` does the walk without the rebalancing and ignores a value that is already there.

## The library never compares keys

One decision in this design is easy to miss. The kernel does not call a comparison function. Its documentation says: "instead of using a comparison callback function pointer, users are expected to write their own tree search and insert functions which call the provided rbtree functions." ([Documentation/core-api/rbtree.rst, lines 54 to 56](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L54-L56)) So the library sees the shape of the tree and nothing about the keys. The code that uses it finds the place, links the node there with `rb_link_node(&data->node, parent, new);` and then calls `rb_insert_color(&data->node, root);` ([Documentation/core-api/rbtree.rst, lines 137 to 138](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L137-L138)). The library cannot check that the order is right, because it is never given the order. That is the Problem `validate`: a check, run on any tree, of the one rule that makes it a search tree.

## Why balance matters

The shape of a search tree depends on the order the values arrive in. Insert 1, 2, 3, 4, 5 and each new value is larger than everything so far, so it goes to the right of the last one: the tree is a chain, with height n. A search then takes n steps in the **worst case**, no better than reading a list. Insert the same values in the order 3, 2, 4, 1, 5 and the height is 3. The Problems let you measure both.

A **self-balancing** tree changes its own shape on insertion so that this cannot happen. The kernel's documentation says what the red-black tree is: "Red-black trees are a type of self-balancing binary search tree, used for storing sortable key/value data pairs." ([Documentation/core-api/rbtree.rst, lines 12 to 13](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L12-L13)) The source file gives the rules and what they prove. Two of the five rules are: "4) Both children of every red node are black" and "5) Every simple path from root to leaves contains the same number of black nodes." ([lib/rbtree.c, lines 21 to 23](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/lib/rbtree.c#L21-L23)) The comment draws the conclusion: "4 and 5 give the O(log n) guarantee, since 4 implies you cannot have two consecutive red nodes in a path and every red node is therefore followed by a black. So if B is the number of black nodes on every simple path (as per 5), then the longest possible path due to 4 is 2B." ([lib/rbtree.c, lines 25 to 28](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/lib/rbtree.c#L25-L28)) Every path has B black nodes and the longest has at most 2B nodes, so no path is more than twice as long as another (arithmetic on that comment), and the height is O(log n) in the **worst case**.

The price of that guarantee is bounded, and the documentation counts it: the red-black tree gives "faster real-time bounded worst case performance for insertion and deletion (at most two rotations and three rotations, respectively, to balance the tree), with slightly slower (but still O(log n)) lookup time." ([Documentation/core-api/rbtree.rst, lines 19 to 22](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L19-L22)) A **rotation** swaps a node with one of its children and keeps the search rule true. Rebalancing needs a way back up from the new node, and the documentation says where it comes from: "The new node also needs a link to its parent node for rebalancing purposes." ([Documentation/core-api/rbtree.rst, lines 113 to 114](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L113-L114)) The node's own declaration has three words, one of them named for both the parent and the colour: `unsigned long  __rb_parent_color;`, `struct rb_node *rb_right;` and `struct rb_node *rb_left;`. ([include/linux/rbtree_types.h, lines 6 to 8](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/include/linux/rbtree_types.h#L6-L8))

The documentation lists what the kernel uses the tree for, quoting an article: "The high-resolution timer code uses an rbtree to organize outstanding timer requests." ([Documentation/core-api/rbtree.rst, lines 29 to 30](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/Documentation/core-api/rbtree.rst#L29-L30))

## What the Problems build

The program from the last Chapter holds one tree, and you now make it a search tree. `insert` adds values one by one with the walk above, and `find` searches and reports how many nodes it visited, so you can see the chain and the balanced tree cost different amounts. `validate` checks a tree that was loaded with `tree`, which can hold anything.
