# Expression trees: SQLite caps their depth

A **binary tree** is a value and two children, each of which is itself a binary tree or nothing. The definition refers to itself, so the natural way to work on a tree is **recursion**: to answer a question about a node, ask it about the two children and combine their answers. This Chapter reads how SQLite (version 3.46.0) keeps the expressions of an SQL statement, such as `1 + 2 * 3`, as a binary tree, and the limit it puts on how tall that tree may grow.

## The node

SQLite says what the structure is for: "Each node of an expression in the parse tree is an instance of this structure." ([src/sqliteInt.h, lines 2934 to 2936](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/sqliteInt.h#L2934-L2936)) What makes it a binary tree is two pointers, declared as `Expr *pLeft;           /* Left subnode */` and `Expr *pRight;          /* Right subnode */`. ([src/sqliteInt.h, lines 3018 to 3019](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/sqliteInt.h#L3018-L3019)) A node for an operator is made from its two operands: the function that allocates one takes `Expr *pLeft,            /* Left operand */` and `Expr *pRight            /* Right operand */`. ([src/expr.c, lines 1031 to 1036](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/expr.c#L1031-L1036)) So `1 + 2 * 3` is a `+` node whose left child is `1` and whose right child is a `*` node with the children `2` and `3`. The picture is the idea, not SQLite's exact layout of it.

In the Problems a node is a value and two children, and a child may be missing.

## Height, by recursion

The same structure holds a number, `int nHeight;           /* Height of the tree headed by this node */`. ([src/sqliteInt.h, line 3031](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/sqliteInt.h#L3031)) The comment above the function that sets it gives the rule: "An expression with no children, Expr.pList or Expr.pSelect member has a height of 1. Any other expression has a height equal to the maximum height of any other referenced Expr plus one." ([src/expr.c, lines 835 to 839](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/expr.c#L835-L839)) For a binary tree that is a recursive definition. The height of nothing is 0: the code starts from `int nHeight = p->pLeft ? p->pLeft->nHeight : 0;` when a child is missing. ([src/expr.c, line 845](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/expr.c#L845)) A single node has height 1, and any other node has the height of its taller child plus one.

Written as code, that is a function that calls itself on both children. It visits every node once, so it takes O(n) time in the **worst case**, and it goes as deep as the tree is tall: one call is waiting for each level on the path it is on, so the stack needs space for `height` calls. That is why the height of a tree is also the cost of recursion on it. This is the Problem `height`.

## Keeping the height instead of finding it

SQLite does not run that recursion each time it needs a height. It stores the result in the node when the node is made. When a node is joined to its subtrees, the code reads the heights the children already hold: `pRoot->nHeight = pRight->nHeight+1;` ([src/expr.c, line 1007](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/expr.c#L1007)) and then `if( pLeft->nHeight>=pRoot->nHeight ){ pRoot->nHeight = pLeft->nHeight+1;`. ([src/expr.c, lines 1016 to 1017](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/expr.c#L1016-L1017)) The function that makes a node takes its operands as arguments (the lines cited above), so the children exist, with their heights set, before the parent is made. That makes the height of a new node O(1) in the **worst case**: two reads and a comparison, whatever the size of the subtrees.

## The limit

The function that builds an operator node then checks the new height: `sqlite3ExprCheckHeight(pParse, p->nHeight);`. ([src/expr.c, line 1044](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/expr.c#L1044)) The check refuses a tree that is too tall and says so in the error it raises: `if( nHeight>mxHeight ){`, `"Expression tree is too large (maximum depth %d)", mxHeight`. ([src/expr.c, lines 789 to 791](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/expr.c#L789-L791)) The maximum is set in one place, with a default and a way to turn it off: "A value of 0 means that there is no limit." ([src/sqliteLimit.h, lines 59 to 64](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/sqliteLimit.h#L59-L64)) and `# define SQLITE_MAX_EXPR_DEPTH 1000`. ([src/sqliteLimit.h, lines 65 to 67](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/sqliteLimit.h#L65-L67))

The documentation says why a limit is needed at all: "During code generation, SQLite walks this tree recursively. The depth of expression trees is therefore limited in order to avoid using too much stack space." ([SQLite, Limits in SQLite, "Maximum Depth Of An Expression Tree"](https://www.sqlite.org/limits.html); the page is not versioned, so it describes the current release and the code above is the 3.46.0 side of it.)

The decision is to spend one integer per node and one comparison per new node so that every recursive walk over a statement has a bounded stack, whatever SQL a user sends. The tree is refused when it is built, before any walk starts.

One walk in the source shows the recursion at work. For each node it calls a callback, recurses into the left child, and then loops on the right child instead of recursing: `rc = pWalker->xExprCallback(pWalker, pExpr);` ([src/walker.c, line 69](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/walker.c#L69)) and `if( pExpr->pLeft && sqlite3WalkExprNN(pWalker, pExpr->pLeft) ){`, `pExpr = pExpr->pRight;`, `continue;`. ([src/walker.c, lines 73 to 79](https://github.com/sqlite/sqlite/blob/bebe2d8be8acfd02592c4972f4ba32c3b4e4a33f/src/walker.c#L73-L79)) Reading those lines: the nested calls follow only the left links, so this walk's stack grows with the number of left steps on a path, not with the height. That is the reading of this chapter, not a claim by SQLite, and it holds only for the left and right links of this one function.

## What the Problems build

You start one program that holds a single binary tree and reads commands from standard input. It grows through the Topic: a search tree, a B-tree, traversals, ancestors, and a text form. `height` gives you the tree and its height, and `limit` is SQLite's refusal: a tree taller than the limit is not accepted. `mirror`, an optional Problem, swaps every node's children.
