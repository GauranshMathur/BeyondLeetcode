# Flat trees and common ancestors: the device tree and git

A tree lives in memory as nodes that point at each other. Sometimes it has to leave memory: be written to a file, sent over a wire, or handed from one program to another. Then it must be turned into a flat sequence and read back into the same tree. That is **serialisation**. This Chapter reads one real flat tree, the **flattened device tree** that describes hardware to the Linux kernel (v6.6), and how little it needs to say to be readable. A second, shorter section reads `git merge-base` (2.47.0) for the question that goes with trees: where do the paths from two nodes to the root first meet?

## A tree as a list of tokens

The device tree's blob is a sequence of tokens, and the header that defines them names two for the shape of the tree: `#define FDT_BEGIN_NODE	0x1		/* Start node: full name */` and `#define FDT_END_NODE	0x2		/* End node */`. ([scripts/dtc/libfdt/fdt.h, lines 53 to 54](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/scripts/dtc/libfdt/fdt.h#L53-L54)) The two tokens bracket a node and everything inside it, children included, as the depth counting below shows, and nothing else is needed to rebuild the shape: a reader only has to count. The function that steps from one node to the next keeps a `depth` and changes it at those two tokens: `case FDT_BEGIN_NODE:`, `if (depth)`, `(*depth)++;` and `case FDT_END_NODE:`, `if (depth && ((--(*depth)) < 0))`. ([scripts/dtc/libfdt/fdt.c, lines 265 to 271](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/scripts/dtc/libfdt/fdt.c#L265-L271)) The depth goes up when a node begins and down when it ends, so after any token it says how deep the reader is, and a tree is one pass over the list. Writing such a list is a depth-first walk that writes a begin token on the way into a node and an end token on the way out of it (the reading of this Chapter, not a statement of the library's).

The Problem `save` writes a binary tree the same way. A node is written as `(`, its value, its left subtree, its right subtree and `)`, and a missing child is written as `.`, so the text of `5` with a child `3` on its left is `(5 (3 . .) .)`. The text format is invented for the Problem, as the begin and end markers are the borrowed part. The text of a tree with n nodes has O(n) characters in the **worst case** (every node has a constant-size part, apart from its value), and writing and reading each visit every node once.

## No parent links: ask by counting

The device tree has no pointer from a node to its parent, because the nodes are just positions in the list. The library still answers "who is the parent?", and the way it does shows what the depth counter is good for. The function does it in two steps: `int nodedepth = fdt_node_depth(fdt, nodeoffset);` then `return fdt_supernode_atdepth_offset(fdt, nodeoffset, nodedepth - 1, NULL);`. ([scripts/dtc/libfdt/fdt_ro.c, lines 646 to 651](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/scripts/dtc/libfdt/fdt_ro.c#L646-L651)) The second function walks from the very start of the blob and remembers the last node it saw at the depth wanted: `for (offset = 0, depth = 0;`, `if (depth == supernodedepth)`, `supernodeoffset = offset;`. ([scripts/dtc/libfdt/fdt_ro.c, lines 605 to 609](https://github.com/torvalds/linux/blob/ffc253263a1375a65fa6c9f62a893e9767fbebfa/scripts/dtc/libfdt/fdt_ro.c#L605-L609)) The ancestor of a node at a given depth is the last node begun at that depth before the node itself. So one lookup is a scan, O(n) in the **worst case**, and the price of leaving out parent links is paid at every question about ancestors. This is a reading of the lines above, not a statement of the library's.

That is the idea behind the Problem `lca`. The **ancestors** of a node are the nodes on the path from the root to it, the node itself included. The **lowest common ancestor** of two nodes is the deepest node that is an ancestor of both. Where the two root paths agree, they agree from the root down, so the answer is the last node they share.

## git: the best common ancestor

`git merge-base` answers the same question for commit history, and its documentation defines "best" for any history: "'git merge-base' finds the best common ancestor(s) between two commits to use in a three-way merge. One common ancestor is 'better' than another common ancestor if the latter is an ancestor of the former." ([Documentation/git-merge-base.txt, lines 21 to 23](https://github.com/git/git/blob/777489f9e09c8d0dd6b12f9d90de6376330577a2/Documentation/git-merge-base.txt#L21-L23); the source marks words with single quotes for emphasis, which are kept as the source has them) The documentation adds: "Note that there can be more than one merge base for a pair of commits." ([Documentation/git-merge-base.txt, lines 25 to 26](https://github.com/git/git/blob/777489f9e09c8d0dd6b12f9d90de6376330577a2/Documentation/git-merge-base.txt#L25-L26)) In a tree every node has one parent and so one path to the root, and the common ancestors of two nodes lie in one chain, so the lowest one is unique. That is arithmetic, and it is why the Problem asks for one answer.

The code walks up from both commits and marks which side reached each one. It starts with `one->object.flags |= PARENT1;` ([commit-reach.c, line 68](https://github.com/git/git/blob/777489f9e09c8d0dd6b12f9d90de6376330577a2/commit-reach.c#L68)) and `twos[i]->object.flags |= PARENT2;` ([commit-reach.c, line 76](https://github.com/git/git/blob/777489f9e09c8d0dd6b12f9d90de6376330577a2/commit-reach.c#L76)), passes the marks on to each parent with `p->object.flags |= flags;` ([commit-reach.c, line 126](https://github.com/git/git/blob/777489f9e09c8d0dd6b12f9d90de6376330577a2/commit-reach.c#L126)), and tests for a commit reached from both sides with `flags = commit->object.flags & (PARENT1 | PARENT2 | STALE);` and `if (flags == (PARENT1 | PARENT2)) {`. ([commit-reach.c, lines 95 to 96](https://github.com/git/git/blob/777489f9e09c8d0dd6b12f9d90de6376330577a2/commit-reach.c#L95-L96)) That commit is a common ancestor. The next lines keep its own ancestors from being reported too: `/* Mark parents of a found merge stale */`. ([commit-reach.c, line 101](https://github.com/git/git/blob/777489f9e09c8d0dd6b12f9d90de6376330577a2/commit-reach.c#L101)) That is the "better than" rule of the documentation, applied by marking.

A binary tree has links downwards only, so the Problem finds the two root paths by search and compares them. That costs O(n) in the **worst case**, since a search may visit every node.

## What the Problems build

`lca` prints the lowest common ancestor of two values in the tree, or `none` if either is missing. `save` prints the tree as text with the begin and end markers above, and `restore` reads such text back into a tree. `restore` obeys `limit` as `tree` does, so text that is read in is checked the way a tree that is loaded is.
