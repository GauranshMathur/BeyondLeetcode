# Boost.Graph: a matrix or a list

A **graph** is a set of **vertices** joined by **edges**. In this Topic a vertex is a **node** with a name, and an edge goes from one node to another, so it has a direction. Before any algorithm can run, the program has to decide how to hold the graph in memory. There are two classic ways, and this Chapter reads how Boost.Graph, a C++ graph library, offers both and says when to use which. It uses Boost 1.85.0. The Build you start in the Problems keeps each node's edges in a map from a name to a list, and the map is the one [Hash tables](/chapters/hash-tables-cpython-dict) taught.

## The property that decides: how many edges there are

The library's guide to graph data structures opens with the deciding property: "The primary property of a graph to consider when deciding which data structure to use is sparsity, the number of edges relative to the number of vertices in the graph." It names the two ends: "A graph where E is close to V2 is a dense graph". Here E is the number of edges, V is the number of vertices, and V2 is V squared, which is the most edges a directed graph can have if an edge from a vertex to itself counts. ([Graph Theory Review, section Graph Data Structures, lines 196 to 199 (Boost 1.85.0)](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/graph_theory_review.html#L196-L199); the page italicises "sparsity" and "dense", and the quotes here drop the markup.) Then it says what to do about it: "For dense graphs, the adjacency-matrix representation is usually the best choice, whereas for sparse graphs the adjacency-list representation is a better choice." ([same page, lines 201 to 204](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/graph_theory_review.html#L201-L204))

## The adjacency matrix: one cell for every pair

The guide describes the matrix like this: "An adjacency-matrix representation of a graph is a 2-dimensional V x V array." Each cell "stores a Boolean value saying whether the edge (u,v) is in the graph." ([same page, lines 213 to 215](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/graph_theory_review.html#L213-L215)) The price and the prize come in the next sentences: "Any edge can be accessed, added, or removed in O(1) time." ([lines 219 to 220](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/graph_theory_review.html#L219-L220)) and "To add or remove a vertex requires reallocating and copying the whole graph, an O(V2) operation." ([lines 220 to 222](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/graph_theory_review.html#L220-L222)) (V2 is V squared again: the page writes it as a superscript.) Asking whether there is an edge from `u` to `v` is a single look-up in the **worst case**, and the space is V × V cells whether the graph has few edges or many.

The library's code agrees on the size. The constructor of its `adjacency_matrix` class sizes the array like this:

```cpp
m_matrix(Directed::is_directed ? (n_vertices * n_vertices)
                               : (n_vertices * (n_vertices + 1) / 2))
```

A directed graph gets V × V cells. An undirected one gets V(V + 1) / 2, because the code that finds a cell swaps `u` and `v` so that `v` is never greater than `u`, which makes the edge from `u` to `v` and the edge from `v` to `u` the same cell. ([boost/graph/adjacency_matrix.hpp, lines 561 to 562](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/include/boost/graph/adjacency_matrix.hpp#L561-L562); the swap is in [lines 641 to 645](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/include/boost/graph/adjacency_matrix.hpp#L641-L645).) The Problem `matrix` prints the directed kind.

## The adjacency list: only the edges that exist

The other representation keeps, for each vertex, only the edges that are there: "An adjacency-list representation of a graph stores an out-edge sequence for each vertex." So "For sparse graphs this saves space since only O(V + E) memory is required." ([same page, lines 246 to 248](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/graph_theory_review.html#L246-L248)) The list has one entry per vertex and one per edge, so V + E. The cost shows in the next sentence: "Edge insertion is O(1), though accessing any given edge is O(alpha), where alpha is the sparsity factor of the matrix (which is equal to the maximum number of out-edges for any vertex in the graph)." ([lines 249 to 252](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/graph_theory_review.html#L249-L252)) To find out whether one edge exists you have to walk the list of out-edges of its start vertex, which has at most V entries in the **worst case**.

The matrix's page names the other cost of the matrix, and it is the one that matters for the Chapters ahead: "The second is that operations that traverse all the out-edges of each vertex (such as breadth-first search) run in O(V2) time instead of O(V + E) time for the adjacency list." ([adjacency_matrix.html, lines 47 to 50](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/adjacency_matrix.html#L47-L50)) With a matrix, listing one vertex's out-edges means reading its whole row of V cells, even when it has no edges at all. Every search in the next Chapters does that for each vertex it reaches.

## Repeated edges: a choice inside the list

Boost's list is itself a choice. The class `adjacency_list` takes a selector for the container of each vertex's out-edges: "The selector for the container used to represent the edge-list for each of the vertices." ([adjacency_list.html, lines 101 to 102](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/adjacency_list.html#L101-L102)) The selector decides whether the same edge can be added twice: "The setS and hash_setS variants disallow parallel edges while the others allow parallel edges." ([adjacency_list.html, lines 463 to 465](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/adjacency_list.html#L463-L465)) (Parallel edges are edges with the same start and end.) When parallel edges are disallowed, adding a repeat does nothing: "For graphs that do not allow parallel edges, if the edge is already in the graph then a duplicate will not be added and the bool flag will be false." ([lines 798 to 800](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/adjacency_list.html#L798-L800)) The same page says what to pick when stable references to edges do not matter: "If you are not as concerned about descriptor and iterator stability, and are more concerned about memory consumption and graph traversal speed, use vecS for the VertexList and/or OutEdgeList template parameters." ([lines 304 to 307](https://github.com/boostorg/graph/blob/a649be53bd90ab3365c6c0c44414c80907cfd8a1/doc/adjacency_list.html#L304-L307))

## What the Problems build

You start one program that reads commands about a directed graph, and you keep growing it through the Topic. `edges` is the adjacency list: `edge` adds an edge, and a repeat of an edge that is already there changes nothing, which is the rule of the set-based variants above. The Reference Code checks for a repeat by walking the start node's list, at most V entries in the **worst case**, and then appends the new edge, which is constant time **amortised**, because the list grows the way [Dynamic arrays](/chapters/dynamic-arrays-cpython-list) showed. `matrix` builds the other representation from the same graph and counts the cells each would use: V + E for the list, V × V for the matrix, which is Boost's directed case. Run `cells` on a graph with 1,000 nodes and 1,000 edges, then on one with 1,000 nodes and 900,000 edges, and you have seen the guide's advice in numbers.
