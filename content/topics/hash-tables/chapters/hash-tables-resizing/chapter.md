# Resizing: when, how much, and what it costs

Both tables so far have a fixed number of slots, and both slow down as they fill: more keys per bin in Java, more probes per lookup in CPython. The fix is the one the Dynamic arrays Topic used for a full block: build a bigger table and move everything across. The [CPython list Chapter](/chapters/dynamic-arrays-cpython-list) showed how a growth rule that multiplies the size gives O(1) amortised appends. This Chapter reads the same decision in a hash table, where there are two new questions. When is a table "full enough"? And, because every key's slot depends on the table size, how do the keys move?

## When: a load factor

Java makes the trigger a number you can read and set. "The load factor is a measure of how full the hash table is allowed to get before its capacity is automatically increased. When the number of entries in the hash table exceeds the product of the load factor and the current capacity, the hash table is rehashed (that is, internal data structures are rebuilt) so that the hash table has approximately twice the number of buckets." The default is .75, which "offers a good tradeoff between time and space costs." ([HashMap.java, lines 62 to 70](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L62-L70); [`DEFAULT_LOAD_FACTOR = 0.75f`, line 250](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L247-L250)) In `putVal` the test is the last step, after the new node is linked: `if (++size > threshold) resize();`. ([line 668](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L667-L669)) With 16 bins the threshold is 12, so the 13th key triggers the resize.

CPython fixes the number instead of exposing it: `#define USABLE_FRACTION(n) (((n) << 1)/3)`, two thirds. The comment weighs the choice: "Increasing this ratio makes dictionaries more dense resulting in more collisions. Decreasing it improves sparseness at the expense of spreading indices over more cache lines and at the cost of total memory consumed." ([Objects/dictobject.c, lines 565 to 576](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L565-L576)) The limit is on the entries array, whose length is `USABLE_FRACTION(dk_size)`, as the first Chapter showed. An 8-slot table holds 5 entries, and the sixth new key forces a resize. One difference matters: a delete does not give its row back. `delitem_common` writes the Dummy marker into the slot and clears the row's key and value, and touches neither `dk_nentries` nor `dk_usable`. ([lines 2616 to 2633](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L2616-L2633)) The check that decides a resize is `dk_usable <= 0`, before the new key is stored. ([lines 1682 to 1686](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L1682-L1686)) So deleted keys count towards the limit until a resize clears them.

## How much: double, more or less

Java's resize does what the documentation says: new capacity is `oldCap << 1`, and the threshold doubles with it. ([resize, lines 683 to 702](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L683-L702))

CPython sizes the new table from how many keys are alive, not from the old size: `#define GROWTH_RATE(d) ((d)->ma_used*3)`. The comment: "This means that dicts double in size when growing without deletions, but have more head room when the number of deletions is on a par with the number of insertions." It also keeps a record of earlier rules: used*4 up to 3.2, used*2 in 3.3.0, and used*2 + capacity/2 in 3.4.0 to 3.6.0. ([lines 613 to 623](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L613-L623)) The new size is the smallest power of two at or above that number, computed by `calculate_log2_keysize`. ([lines 578 to 584](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L578-L584), called from [insertion_resize, lines 1673 to 1676](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L1673-L1676)) With 5 live keys that is 15, so 16 slots. With 21 live keys it is 63, so 64.

## Moving the keys

A key's slot is its hash masked by the table size, so a bigger table puts keys in different places. Java's resize exploits a property of doubling. Its comment: "because we are using power-of-two expansion, the elements from each bin must either stay at same index, or move with a power of two offset in the new table." ([lines 674 to 679](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L674-L679)) The code tests one bit, `(e.hash & oldCap) == 0`: those nodes stay in bin `j`, the rest go to bin `j + oldCap`. Each of the two groups is relinked in its old order, marked `// preserve order`. ([lines 721 to 749](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L721-L749)) A resize touches every node once.

CPython rebuilds. `dictresize` is documented as: "Restructure the table by allocating a new table and reinserting all items again. When entries have been deleted, the new table may actually be smaller than the old one." ([lines 1936 to 1938](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L1936-L1938)) For a table of general keys such as ints, it copies the entries that still have a value into the front of a new entries array, in order, and then `build_indices_generic` places each entry's index in the new table with the same probe rule. ([lines 2035 to 2050](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L2035-L2050) and [1905 to 1918](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L1905-L1918)) So a resize also removes the deleted rows and the Dummy slots.

## What it costs

A resize costs O(n): every live key is placed again. It is not paid on every insert. After a Java resize from capacity `c` to `2c`, the threshold is `0.75 * 2c = 1.5c`, and the table holds `0.75c` keys, so the next resize is `0.75c` puts away. Resizes happen at geometrically growing sizes, so the keys moved in total add up to at most about twice the keys put, and `put` is O(1) amortised. The argument is the same as for the growth of a list. It leans on the "approximately twice" from the quote above. A fixed step would not give it. CPython's rule has the same shape when nothing is deleted, because it doubles, as the comment above says. (This is the derivation of the complexity. Neither project's documentation states it for the table.)

Java also documents how to avoid the cost when you know the count: "If the initial capacity is greater than the maximum number of entries divided by the load factor, no rehash operations will ever occur." ([lines 76 to 78](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L76-L78))

## A rounding step that was wrong in 3.13.0

The line that picks the power of two in CPython 3.13.0 is:

```c
minsize = (minsize | PyDict_MINSIZE) - 1;
return _Py_bit_length(minsize | (PyDict_MINSIZE-1));
```

([lines 580 to 584](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Objects/dictobject.c#L580-L584))

For a `minsize` of 8 or more, this gives the smallest power of two that is at least `minsize`. For a small `minsize` it does not: a dict with 1 live key asks for `minsize = 3`, then `(3 | 8) - 1 = 10`, `10 | 7 = 15`, and a bit length of 4 means 16 slots, not 8. The same happens with 2 live keys. A dict that is churned (many inserts and deletes) down to one or two keys is rebuilt in a table twice as big as needed. A later patch release fixed it: the same function in [3.13.18](https://github.com/python/cpython/blob/0d4bd512fc429e3d4eacdd113c975e161f21644d/Objects/dictobject.c#L580-L584) reads `minsize = Py_MAX(minsize, PyDict_MINSIZE); return _Py_bit_length(minsize - 1);`. The commit "gh-133703: dict: fix calculate_log2_keysize()" replaced the two lines with `minsize = Py_MAX(minsize, PyDict_MINSIZE); return _Py_bit_length(minsize - 1);`, and its news entry reads "Fix hashtable in dict can be bigger than intended in some situations." ([commit 92337f6](https://github.com/python/cpython/commit/92337f666e8a076a68305a8d6dc8bc9c095000e9)) The Build follows 3.13.0 as written, including this step.

## What you build

First Java's load factor, which reuses the resize you wrote for the ninth-node rule. Then CPython's growth, with the entries array, the compaction and the 3.13.0 rounding.
