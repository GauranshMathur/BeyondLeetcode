# Hash functions, and keys chosen against you

So far the hash of an int was the int. Real programs hash strings, and a hash function is a fixed rule that anyone can read. This Chapter looks at what happens when someone reads it to pick keys that all land in one place, and at the two defences that Python and Java chose.

## A hash function is a rule you can run backwards

Java documents the hash of a string in its source. It "is computed as `s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]` using `int` arithmetic, where `s[i]` is the `i`th character of the string, `n` is the length of the string". ([String.java, lines 2342 to 2350](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/lang/String.java#L2342-L2350)) So the number is fixed by the text of the key, on every machine and every run.

That makes collisions easy to build. The letters `A` and `a` are 65 and 97, so `"Aa"` hashes to `65*31 + 97 = 2112`. The letters `B` and `B` are 66, so `"BB"` hashes to `66*31 + 66 = 2112`. The formula adds up the string left to right, so swapping one two-letter block for another block with the same hash changes nothing. Ten blocks, each `"Aa"` or `"BB"`, give 2^10 = 1024 different strings of 20 characters with one hash code. (This is arithmetic on the formula above, not a claim about Java's source.)

## The attack

In December 2011 two researchers presented it as an attack on web servers. Their talk's abstract: "a common flaw in the implementation of most of the popular web programming languages and platforms (including PHP, ASP.NET, Java, etc.) can be (ab)used to force web application servers to use 99% of CPU for several minutes to hours for a single HTTP request." ([28C3: Effective Denial of Service attacks against web application platforms, Klink and Wälde](https://events.ccc.de/congress/2011/Fahrplan/events/4680.en.html)) The advisory that coordinated the fixes puts the cause in one sentence: "the condition can be leveraged by exploiting predictable collisions in the underlying hashing algorithms." It lists Java and Python among the affected languages, and for Java the fixed version is "N/A". ([oCERT-2011-003](https://ocert.org/advisories/ocert-2011-003.html))

The cost is the chain. If `n` keys share a bin, each `put` walks the chain, so `n` puts cost O(n²) in total, a worst case. Python's documentation gives the same figure for its own table: inputs "that exploit the worst case performance of a dict insertion, O(n2) complexity". ([Data model, `object.__hash__`, Python 3.13](https://docs.python.org/3.13/reference/datamodel.html#object.__hash__))

## Python's answer: salt the hash

CPython's fix was to make the hash of a string depend on a secret that changes every run. The documentation: "By default, the `__hash__()` values of str and bytes objects are 'salted' with an unpredictable random value. Although they remain constant within an individual Python process, they are not predictable between repeated invocations of Python." and "Hash randomization is enabled by default" since 3.3. ([Data model, `object.__hash__`, Python 3.13](https://docs.python.org/3.13/reference/datamodel.html#object.__hash__)) The environment variable `PYTHONHASHSEED` controls it: "If this variable is not set or set to random, a random value is used to seed the hashes of str and bytes objects." ([Command line and environment, Python 3.13](https://docs.python.org/3.13/using/cmdline.html#envvar-PYTHONHASHSEED))

In the source, the default algorithm is SipHash 1-3 (`#define Py_HASH_ALGORITHM Py_HASH_SIPHASH13`, unless the platform needs aligned access). ([Include/pyhash.h, lines 40 to 48](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Include/pyhash.h#L40-L48)) It is keyed with two 64-bit values from the process's hash secret: `siphash13(_Py_HashSecret.siphash.k0, _Py_HashSecret.siphash.k1, src, src_sz)`. ([Python/pyhash.c, lines 475 to 483](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Python/pyhash.c#L475-L483)) Rust's standard `HashMap` made the same choice: "HashMap uses a hashing algorithm selected to provide resistance against HashDoS attacks. The algorithm is randomly seeded". ([HashMap, Rust 1.80.0](https://doc.rust-lang.org/1.80.0/std/collections/struct.HashMap.html))

Look at what the documentation lists: str and bytes. Ints are not salted. The first Chapter's source comment says that ints "are their own hash codes", and the numeric hash is a reduction modulo a fixed prime `P = 2**61 - 1` on a 64-bit build, which agrees with that for ints below `P`. ([Python/pyhash.c, lines 31 to 34](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Python/pyhash.c#L31-L34), with `PyHASH_BITS` at [Include/cpython/pyhash.h, lines 12 to 13](https://github.com/python/cpython/blob/60403a5409ff2c3f3b07dd2ca91a7a3e096839c7/Include/cpython/pyhash.h#L12-L13)) So `0`, `P`, `2P` and every other multiple of `P` have hash 0. And the probe rule depends only on the hash, so they walk the same path through the table. Nobody has to guess a secret to build them. (A derivation from the two sources; the Build's keys stay below 2^31 and cannot show it.)

## Java's answer: make the worst case smaller

Java did not salt. Its proposal, JEP 180, says why. The earlier JDK 8 work, "the alternative string-hashing implementation, improved collision performance for string-valued keys only, and it did so at the cost of adding a new (private) field to every String instance." The tree bins "will improve collision performance for any key type that implements Comparable". ([JEP 180](https://openjdk.org/jeps/180), section "Motivation")

The tree bins were the previous Chapter. They keep the hash deterministic and cap the damage at O(log n) per operation for keys that are `Comparable`, a worst-case bound. A `String` is one: the code that checks the class has a shortcut, `// bypass checks`, for `String.class`. ([HashMap.java, lines 345 to 349](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L345-L349)) Take the 1024 strings above. In a table below 64 bins, the ninth one in a bin doubles the table. That does nothing for keys that share a hash code, since doubling cannot separate them. Once the table has 64 bins, the next one makes a tree. You will watch both happen.

## The cost of each defence

Salting changes what the program prints: "Changing hash values affects the iteration order of sets. Python has never made guarantees about this ordering". ([Data model, `object.__hash__`, Python 3.13](https://docs.python.org/3.13/reference/datamodel.html#object.__hash__)) Trees cost memory and code: "TreeNodes are about twice the size of regular nodes", which is why they appear only in long bins. ([HashMap.java, lines 177 to 179](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L177-L179)) And a tree needs an order: for keys that are neither distinct in hash nor Comparable, the notes admit "we may waste about a factor of two in time and space compared to taking no precautions". ([lines 159 to 175](https://github.com/openjdk/jdk/blob/890adb6410dab4606a4f26a942aed02fb2f55387/src/java.base/share/classes/java/util/HashMap.java#L159-L175))
